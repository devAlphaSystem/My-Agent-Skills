# Skills

Reusable agent skills for project mapping, implementation, debugging, code review, testing a web project's server directly, using a running web system the way its customers would, keeping interface work consistent with existing patterns, delegate model selection, and editing prose. Each directory contains a `SKILL.md` file with the skill's trigger, workflow, and rules.

I use these skills in T3 Code with Codex on the Plus plan and Claude on the Max plan. Some skills depend on T3 Code's `delegate_task` to coordinate Codex and Claude delegates in the same workflow. T3 Code is required to run those skills as configured in my setup.

## Usage

Make the desired skill directories available to your agent's skill loader, keeping each `SKILL.md` inside its directory. The loading mechanism depends on the host. This repository contains instruction files and has no installation script or application to build.

For the workflow skills, include the skill name in your request and describe the task:

```text
onboard this project and document its structure and verified commands.

squad add input validation to the settings form using the existing patterns.

change add a CSV export button to the orders page.

debug why saving the settings form fails with an empty optional field.

qa the settings form changes, including invalid inputs and error states.

server-test test the server of this project and report every problem.

customer-test use the system running at http://localhost:3000 as its customers would.

ui-consistency map this project's interface patterns and save them in UI.md.

ui-consistency squad add a customers page with an edit drawer and a delete confirmation.

council review the settings form changes for correctness and maintainability.

pickmodel squad add input validation to the settings form using the existing patterns.

pragmatic squad improve the settings form using the existing patterns.

pragmatic council review the changes and keep effort proportional to practical impact.

pragmatic qa test the changes and defer rare, low-impact defects that need disproportionate effort.
```

Invoke `unslop` through your host's skill mechanism and provide the text to edit. The agent can also select it on its own when asked to make writing sound less AI-generated, and `onboard` applies its rules before saving `PROJECT.md`.

The agent can also apply `ui-consistency` at a light level whenever a task builds or changes an interface's appearance or behavior. Its examples are not an exhaustive checklist: it discovers the project's actual patterns for the affected components, composition, states, and interactions, including client-only behavior and project-specific elements the skill does not name. Whether the host loads the skill on its own is up to the host, so this is not guaranteed. At the light level the agent does the discovery, the decisions, the checks, and the recording itself, starts no reviewers, and opens no browser. The code changes go to an implementer delegate, because the agent in the chat never edits code. It checks the behavior in code only and says so. It records what it finds in `UI.md`, and creates the file when it does not exist.

Saying `ui-consistency` with a task adds two delegates, a code reviewer and a visual checker, using platform-appropriate screenshots, measurements, recordings, or observed interactions. Web checks use the browser; native Android checks use a test device and supported configurations, without requiring desktop widths or DOM measurements. This costs more time and tokens, and it runs the project's app locally. A real or shared database needs your detailed permission first, and without the app, the required browser or device tools, or test accounts the run falls back to code checks and reports what stayed unconfirmed at runtime. Each review round reruns only the reviewers that the fix affects, with at most three rounds. A small change can skip the reviewers, and the report says so.

Reusing a component does not prove its states are usable. Runtime checks verify that feedback is perceivable, required controls are reachable, and input navigation works through the interaction's boundaries, including forward and reverse keyboard traversal on web. Code-only and headless DOM checks leave those properties unconfirmed. A material failure in the requested flow remains a failed check when inherited from a reference; fix its authorized root cause and check affected uses, or report it unresolved. Defects outside the task stay follow-ups, and these checks do not authorize a broad redesign.

What the skill does with `UI.md` when you say `ui-consistency` with a task:

- If `UI.md` does not exist, it creates focused entries for the task and offers project-wide mapping without blocking the task. Mapping starts only when you accept the offer or explicitly request it.
- If `UI.md` exists but holds only entries from earlier tasks, it asks once per project whether to map the whole project first. If you decline or do not answer, it continues with the focused task and does not start the mapping.
- If `UI.md` already holds mapped entries, it reuses them and verifies the ones the task touches against the code, without mapping again.

Saying `ui-consistency` with no task, or explicitly requesting project-wide mapping, maps the project and confirms the properties and interactions it can check in the running app. Updating a specific pattern stays focused on that entry.

When the project's instruction file does not mention `UI.md`, the skill asks once per project before appending one line that tells agents to read the relevant `UI.md` entries before interface work. It edits nothing without your approval, and it never creates an instruction file. If you decline, it records that and does not ask again. Whether a host loads that file is up to the host, so the line does not guarantee that other agents read `UI.md`.

Workflow skills run as separate requests. `debug` produces a brief for squad but does not implement a fix or start squad. `onboard`, `qa`, `server-test`, `customer-test`, and `change` also require an explicit request. Saying `change` is that request for every skill it runs. Use `pickmodel` together with any skill that starts delegates, in the same request, to choose delegate models.

The squad and qa files define the objective criteria for high complexity, such as open-ended requests, changes across several modules, and costly or hard to undo mistakes.

Any agent, including the coordinator and the delegates, can start Claude Haiku 5.5 high at any time for light information lookups, including internet searches. This needs no permission, is not a delegate role, does not count toward council's two delegates, and needs no `pickmodel` question. Haiku stays read-only. It returns a link for each source, and the agent that started it checks the source before relying on the result.

These model assignments are required unless `pickmodel` is invoked. Without `pickmodel`, if a required model or reasoning level is unavailable, report the limitation instead of substituting another model. The one exception is GPT 6.2 Sol's usage limit. When T3 Code warns that GPT 6.2 Sol has no usage left, its roles run on Claude Sonnet 5.5 xhigh for the rest of the run, with the same brief and limits, and the final report says so. With `pickmodel`, a model with no usage left counts as unavailable and the user picks again.

With `pickmodel`, the user chooses each delegate's model through a selectable-options tool before it starts, then chooses the effort when the model allows more than one (Claude Sonnet 5.5 and GPT 6.2 Sol, high or xhigh). Claude Haiku 5.5 is not offered for roles that edit source files. GPT 6.2 Sol is offered for them but is never the recommended option. The workflow's assigned model and effort become the recommended options when they are allowed and available. Unavailable models are excluded; if none are available, the workflow stops.

Every new delegate requires a fresh answer, including later review rounds and replacements. The one exception is delegates with the same role that start together in one parallel group: you can give them one choice, which covers only that group. All choices for a parallel group must be collected before any delegate in that group starts. Async questions require an actual user response. Pickmodel overrides model assignments only; roles, prompts, delegate counts, workflow, scope, and permissions remain unchanged. The final report includes each delegate's role, model, and effort.

In T3 Code, the skills use `orchestrator_capabilities` to resolve the models and `delegate_task` to start delegates. Using them in another host requires equivalent delegation support for the required models. `unslop` does not define delegate roles or fixed model requirements. The visual checker of `ui-consistency` uses T3 Code's browser (`preview_*`) and device (`device_*`) tools when available, and the skill says what to do in other hosts. The scout, the customers, and the recheckers of `customer-test` work only through the browser tools.

## Choosing a workflow

Use `onboard` when a project needs a shared map in `PROJECT.md`. Use `squad` when the requested change is ready for research, planning, and implementation. If a bug's cause is unknown, start with `debug`, then pass its findings to squad in a separate request.

Use `change` for a feature you want added, edited, or removed and tested in one request, from a new chat. It always starts with squad's researcher, then picks a path. A small, low-risk change, such as a few files in one module that change no auth, payments, data writes, schema, dependency, or widely shared code, takes the light path: one implementer on Claude Sonnet 5.5 high, which escalates to Claude Sonnet 5.5 xhigh when the change adds logic or a fix fails, `ui-consistency` at the light level, and only the qa testers the change needs, with at most two rounds. Anything else, or anything uncertain, takes the full path: squad's planner and implementer, the full `ui-consistency` review for interface changes, and qa with both testers. A light run that turns out bigger moves to the full path and says so. Say `change quick` or `change full` to choose the path yourself. Both paths apply impeccable's design rules to interface work, pragmatic to testing, and the unslop rules to every piece of text. The run ends with a short report, which explains what was done in plain words for someone who does not code, then gives the test results and the notes you need to act on.

After implementation, request `qa` to exercise the changed behavior or `council` for review and feedback. Use `unslop` when editing documentation or other prose.

Use `server-test` in a new chat to test the server of a web project in any language, from the inside. A mapper reads the code and maps the endpoints, data, background work, and external services. The coordinator starts the system on a disposable database that it creates, such as a downloaded portable database binary or a temporary database file, and never connects to the database in the project's configuration. External services are replaced by local stand-ins, and email goes to a local mail catcher, so nothing reaches real data or real services. If the database needs something installed on the computer, such as a container runtime, the run asks first and stops if you say no. Testers call the server directly in eight passes: contract, access, data, background, security, concurrency, resilience, and load. Load runs at light, medium, and heavy levels, the heavy one up to the point where the system breaks, and only against the local system. Every delegate gets a fixed prompt from the skill file. The report gives the likely place of each problem in the code, groups the findings into work packages, and the final reply gives a fix brief to paste once for each package. The run stops and deletes everything it started.

Use `customer-test` in a new chat to learn what the system is like for the people who use it. You start the system, and the skill never starts or stops it. A scout learns the product through the browser, and customers with different personas and purposes use it without reading the code, such as a newcomer, a customer on a phone, one who judges the looks, one who makes mistakes, and one who tries to bend the rules. A run can start dozens of delegates, and invoking the skill is the explicit request for that scale. Name a part of the product in the request to make it the focus of the run, and say so if you already signed in to a browser profile for it. How many run at once depends on the browser's sessions. When all tabs of a browser profile share one session, customers that need their own account take turns in each profile, and the others share an account and run together. Every delegate gets a fixed prompt from the skill file, with only the fields of that run filled in, so every run briefs its delegates the same way. Its report is written for the agent that will fix the findings, with exact screen text, steps, and screenshots. It names no causes, because nobody on the run read the code. A serious finding that only one customer saw is rechecked before the report calls it confirmed, and a recheck that can't tell the product from the browser tool confirms nothing. The report lists findings about sample content apart from the findings about the product, and groups the rest into work packages. The final reply gives a fix brief to paste once for each package, so the agent that fixes never has to read the whole report. Use `server-test` instead when the test should read the code and call the server directly.

Add `ui-consistency` to a request that builds or changes interface, with or without `squad`, so that the work reuses the project's shared elements, variants, and flows instead of recreating them. Saying it also has a code reviewer and a visual checker examine the result. The visual checker opens the running app, compares the new screen with the reference page, measures the fixed properties, and records the flows. It can also check a failed request by making one approved local request fail on the client. That simulates a network failure, not a backend error, and the report says so. Every run adds what it learns to `UI.md`, so the file grows with the project. Entries from a task cover only the comparable uses that task examined, and the file states the count and its scope. Run it once with a request to map the project; it inventories the patterns and confirms the properties and flows it can reach in the running app, listing anything unverified. The skill can offer to add one line to the project's instruction file that points agents to `UI.md`, but only with your approval. Pending and declined offers are recorded so the skill does not ask repeatedly.

Add `pickmodel` to any skill that starts delegates when you want to select the model for each delegate. The other skill does not need to mention it, because it takes precedence over that skill's model rules. It asks before every delegate, but when delegates with the same role start together you can give them one choice, so a wave of customers or testers takes one question.

Add `pragmatic` to keep investigation, fixes, and optimization proportional to practical impact. Clear, low-cost improvements remain required. It overrides optional performance work and permits deferring rare, minor defects when a proper fix would take disproportionate effort. It also avoids speculative scale and unsupported compatibility work, and permits deferring rare, minor defects when a fix would put common flows at greater risk. Documented capacity and support commitments still apply. Known issues and failed checks remain visible. Rarity does not excuse security problems, destructive consequences, or unmet explicit requirements. Hours of work or hundreds of thousands of tokens for an expected gain of 1% to 5% require an explicit request for that depth of optimization. It starts no delegates and can also guide work without another skill.

## Scope and permissions

Each skill defines its own role boundaries. The agent in the chat with you, called the coordinator, never creates or edits code in any skill. It orchestrates, guides, and briefs, and every code change goes to a delegate, even a one-line fix. Researchers, reviewers, and testers generally keep source files unchanged. Squad assigns source edits to its implementer; QA assigns fixes to its fixer; council and `ui-consistency` without squad start an implementer; `pragmatic` alone starts one too. In `server-test`, a builder delegate writes the stand-in servers. `change` edits code only through squad's implementer and qa's fixer. The coordinator still writes the documents the skills define, such as `PROJECT.md` and `UI.md`, and runs commands. Onboard writes only `PROJECT.md`, and debug keeps experiments outside the source tree. Besides the changes a task asks for, `ui-consistency` writes only `UI.md`. It edits the project's existing instruction file only to append the one line pointing to `UI.md` that you approved for that project, and it never creates an instruction file. Its reviewers edit nothing. Its coordinator prepares the runtime and starts and stops the test services or emulators. The visual checker may launch and relaunch the prepared native app through the device tools. The run stops only the app and processes it started. The screenshots and recordings go to an evidence directory outside the source tree, which it keeps because they are the deliverable. `server-test` writes only its run directory, which it creates inside the project and leaves untracked, and a tools directory outside the project that it deletes at the end. Invoking it permits the disposable database it creates and nothing more, and it never connects to the database the project is configured to use. It installs nothing on the computer without asking. Its coordinator starts and stops every process of the run and writes no code, and its testers never edit source files. `customer-test` writes only its run directory, which it creates inside the project and leaves untracked. Its delegates never read the source code and use the system only through the browser, by hand. Its coordinator never starts or stops the system, which the user runs, and the run closes the tabs it opened.

The delegation skills restrict Git to read-only status, diff, show, and log operations. Their files specify the permitted options. They also restrict destructive operations, production writes, publishing, and dependency changes. Project and session instructions may impose stricter limits on commands, servers, or file changes.

Read the relevant `SKILL.md` before invoking a skill for its complete permissions, stopping conditions, and report format.
